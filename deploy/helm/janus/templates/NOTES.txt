The Janus server boots SEALED. Every secret route returns 503 until unseal.

1) Reach the server (no Ingress by default). Port-forward:

     kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "janus.fullname" . }} 8200:{{ .Values.service.port }}

     (With seal.type=shamir the pod stays NotReady until you unseal, so
      `helm install --wait` will time out. That is expected: readiness gates on
      unseal by design. Install without --wait, then unseal.)

   Then point the CLI at it:  export JANUS_ADDR=http://127.0.0.1:8200

2) ONE-TIME initialization (only on a brand-new, empty database). This returns
   the first-admin password and (for Shamir) the unseal shares / recovery
   material EXACTLY ONCE — store them securely:

     janus init            # or: POST /v1/sys/init

3) Unseal:

{{- if eq .Values.seal.type "shamir" }}
   You chose Shamir. After EVERY pod restart the pod stays NotReady until an
   operator supplies the threshold of shares:

     janus unseal          # run once per share until the threshold is met

   Check state any time:

     janus seal-status     # or: GET /v1/sys/seal-status
{{- else }}
   You chose cloud-KMS auto-unseal ({{ .Values.seal.type }}). The pod unwraps the
   master key from KMS on boot and unseals itself — no manual step per restart,
   provided the pod's cloud identity can use the key. Confirm:

     janus seal-status     # or: GET /v1/sys/seal-status  → sealed:false

   If it stays sealed, check the ServiceAccount's cloud-identity annotations and
   the KMS key's access policy.
{{- end }}

Readiness gate: {{ include "janus.fullname" . }} becomes Ready only once it is
initialized AND unsealed (readinessProbe → /v1/sys/ready). Liveness
(/v1/sys/live) is independent of seal state and never blocks on unseal.
